# 홈 게임 목록을 필요한 묶음만 조회하기

홈이 모든 월드컵과 후보를 한 번에 받던 동작을 다음과 같이 변경합니다.

- 처음: 추천 및 주요 카테고리의 첫 묶음만 조회.
- `>`: 해당 줄의 다음 묶음만 추가 조회. 스크롤 근처에 왔다는 이유로 자동 조회하지 않음.
- 카테고리 더보기: 숨겨진 카테고리의 첫 묶음을 그때 조회.
- 기타 카테고리 더보기: 다음 8개만 추가 조회.
- 검색: 아직 받지 않은 게임도 DB에서 제목·설명·후보명·다국어 번역·태그로 검색.
- 정렬: DB의 전체 검색 결과를 인기순 또는 최신순으로 정렬한 뒤 페이지를 나눔.
- 게임 진입: 해당 게임의 전체 후보와, 관련 게임의 작은 카드 정보만 별도 조회.
- 관리·개인 목록·카테고리 전체 페이지는 기존 전체 목록 방식 유지.

최근 생성/플레이 박스는 필요한 제목·날짜만 조회합니다. 계정·로그인 코드, SEO/사이트맵 설정은 수정하지 않습니다.

## 다른 컴퓨터에서 적용하기

터미널이나 로컬 개발 환경을 설치하지 않아도 됩니다.

1. 이 변경사항의 `supabase/20261014_worldcup_home_paging.sql` 파일을 GitHub에서 엽니다.
2. 파일 내용을 전체 복사합니다. GitHub의 `Copy raw file` 버튼을 사용하면 편합니다.
3. Supabase에서 OnePickGame 프로젝트 → **SQL Editor** → **New query**를 엽니다.
4. 붙여 넣고 **Run**을 누릅니다. 성공한 것을 확인하세요.
5. GitHub의 이 PR에서 변경사항을 main에 병합합니다. Draft라면 먼저 **Ready for review**를 누릅니다.
6. main과 연결된 Vercel 자동 배포가 성공했는지 확인합니다.

**SQL을 먼저 실행한 뒤 병합해야 합니다.** 코드를 먼저 배포하면 새 조회 함수를 찾지 못해 홈 목록을 불러오지 못할 수 있습니다.

SQL은 읽기 전용 조회 함수 두 개를 추가/교체합니다. 게임·후보·통계·비밀번호를 삭제하거나 초기화하지 않습니다. 기존 RLS를 따르며, 재실행할 수 있습니다.

## 확인 방법

브라우저 개발자도구 → Network에서 `get_worldcup_home_rows`로 필터링합니다.

- 새로고침: 요청의 `p_requests`는 `featured`, `korea`, `anime_manga`, `person`의 offset 0만 포함합니다.
- 각 줄에서 `>`: 그 줄의 key와 다음 offset 요청이 추가됩니다.
- 카테고리 더보기: 처음 받지 않은 카테고리 key만 요청합니다.
- 기타 더보기: offset 8부터 조회합니다.
- 새로고침만으로 `worldcups?select=*` 전체 목록 요청이 발생하면 안 됩니다.
- 아직 첫 화면에 없는 게임의 제목/후보명으로 검색하고, 인기순·최신순도 확인합니다.
- 카드를 눌러 후보 수와 게임 진행·결과 화면이 정상인지 확인합니다.

## 검증

- `node scripts/test-home-paging.cjs`: 초기/추가 범위, 중복 클릭, 실패 후 재시도, 라우트별 데이터 범위 검증.
- 로컬 React 화면 테스트: 실제 Home 마운트 및 `>`/카테고리/기타 더보기 요청 범위 검증.
- 로컬 PostgreSQL(PGlite): 페이지 순서, 검색, 작성자 필터, 관련 카드, RLS, SQL 재실행 확인.
- React production build 성공. 사이트맵 생성과 운영 DB 실행은 이 작업에서 수행하지 않았습니다.

운영에서 읽은 240개 게임 데이터로 구성한 로컬 DB 테스트에서는, 각 초기 줄 2개씩(최대 8개) 조회 시 JSON이 약 8MB에서 약 0.34MB로 줄었습니다. 이는 압축 해제 크기이며, 화면 폭·후보 수에 따라 달라집니다. 운영 반영 후 실제 응답 시간을 별도로 확인해야 합니다.

배포를 되돌려야 하면 PR의 코드 변경을 되돌리면 됩니다. 추가한 조회 함수는 호출하지 않으면 기존 화면에 영향을 주지 않습니다.
