# 월드컵 홈·제작 페이지 공통 카드 정보

## 이번 방식
이전 수정에서 제작 페이지가 별도로 `winner_stats`를 읽던 코드를 제거했습니다. 이제 월드컵 홈과 구절판/티어표 제작 페이지의 원본 카드가 **같은 저장된 사진 주소 두 개**를 읽습니다.

원래 홈은 완성된 합성 썸네일 파일을 저장해 두는 구조가 아니라, 통계로 고른 후보 사진 두 장을 화면에 배치하고 있었습니다. 두 주소를 공유할 수 있도록 `worldcup_card_previews` 파생 테이블을 추가했습니다. 새 이미지 파일을 만들거나 복제하지 않습니다.

- 최초 SQL 실행 시 기존 데이터의 1·2위 사진 주소를 채웁니다.
- 이후 결과 기록이 추가·수정·삭제되거나 원본 후보 사진이 바뀌면 저장된 카드 정보를 자동 갱신합니다.
- 우승 횟수 → 대결 승리 횟수 순이며 완전히 같으면 원본 후보 순서로 고정합니다. 통계가 없으면 기본 두 후보를 저장합니다.
- 제작 페이지에서는 순위 계산, `winner_stats` 조회, 썸네일을 위해 후보 전체를 재조회하는 작업을 하지 않습니다.
- 홈은 같은 카드 정보를 화면에 보이는 ID들에 대해 묶어서 읽고, 해당 이미지가 있으면 우선 사용합니다. 홈의 기존 참여 수·설명문용 통계 기능은 유지합니다.
- 원본 페이지를 거치지 않고 제작 페이지로 바로 들어와도 저장된 카드 정보를 읽을 수 있습니다.

## 필수 적용 순서
1. Supabase SQL Editor에서 **`supabase/20261117_worldcup_card_previews.sql`을 한 번 실행**합니다. 기존 결과·후보 데이터를 삭제하거나 초기화하지 않습니다. 새 파생 테이블, 읽기 권한, 자동 갱신 트리거와 초기 카드 정보를 생성합니다. 반복 실행도 가능합니다.
2. ZIP의 파일을 기존 경로로 덮어쓰고 서버·프런트엔드를 함께 빌드·배포합니다. 공통 모듈 `src/utils/sharedWorldcupCards.js`를 반드시 포함합니다.
3. 월드컵 홈과 해당 프리셋을 새로고침해 같은 두 사진인지 확인합니다.

**SQL을 실행하지 않고 파일만 배포하면 제작 페이지에 저장된 카드 사진이 나오지 않습니다.** 별도 서버 비밀키나 환경변수는 필요 없습니다. 이번 작업에서 운영 SQL 실행이나 운영 배포는 하지 않았습니다.

## 캐시와 비용
- 데이터는 두 사진 URL·후보 ID·갱신 시각 등 작은 메타데이터입니다. 이미지 파일을 추가 저장하지 않습니다.
- 브라우저와 서버 프로세스의 공통 메모리 캐시는 최대 160개, 60초입니다. 진행 중인 중복 요청은 합치고 한 요청에 최대 100개 ID를 조회합니다. 순위 변경은 캐시 때문에 최대 약 1분 늦게 보일 수 있으며 페이지를 완전히 새로고침하면 브라우저 캐시 상태는 초기화됩니다.
- 이 메타데이터 캐시와 실제 이미지 파일의 HTTP 캐시는 다릅니다. 같은 이미지 URL이면 유효한 기존 이미지 캐시를 재사용할 수 있지만, 없거나 만료되면 이미지 두 파일의 실제 용량만큼 전송됩니다.
- 일반 사용자는 파생 테이블을 읽기만 가능하며 직접 수정하거나 갱신 함수를 실행할 수 없습니다. 삭제된 원본은 공개 조회에서 제외됩니다.

## 검증
- CRA 빌드 성공.
- PostgreSQL 호환 PGlite: 반복 적용, 기존 카드 생성, 결과 추가/수정/삭제, 후보 사진 수정, ID 없는 예전 후보, 삭제·복구, 공개 읽기와 직접 쓰기 금지, 일반 사용자 결과 저장 시 자동 갱신 확인.
- 코드/UI: 제작 페이지의 통계 조회 금지, 후보 일부만 있어도 저장된 두 주소 사용, 홈과 제작 페이지의 캐시/진행 중 요청 공유, 만료·묶음 조회·캐시 개수 제한·누락된 테이블 대응 확인.
- 실제 빌드 JS를 JSDOM에서 실행: 홈이 저장된 카드 주소를 사용하고 한 번에 묶어서 조회하는지 확인. 한국어/영어 구절판·티어표 프리셋도 저장된 사진만 표시하는지 확인했습니다.
- 실제 운영 DB의 트리거 실행 시간이나 이미지 전송량은 측정하지 않았습니다.
